# Internal Task & Management Dashboard

This is a small internal tool I built for tracking team tasks. It has a React
frontend (Vite + Tailwind) and a FastAPI backend with SQLite. Nothing fancy on
the infra side — the goal was to keep it easy to run and easy to read.

## What it does

- **Dashboard** — headline numbers (total, pending, in progress, completed,
  overdue, "assigned to me"), a breakdown by priority, and the most recently
  updated tasks.
- **Task list** — search + filters for status / priority / assignee, sorting
  and pagination. All of this happens in the API, the frontend doesn't load
  the whole table into memory.
- **Kanban board** — same tasks shown as cards in status columns. Drag a card
  to another column to change its status (the UI updates optimistically and
  rolls back if the request fails). Filters work here too.
- **Task detail page** — everything about a task on one screen: description,
  assignee, due date, inline status change, comments, and a timeline of what
  happened to the task.
- **Login + roles** — JWT auth. Three roles: `admin`, `manager`, `member`.
  Only admins and managers can delete tasks; user management and audit logs
  are admin-only.
- **Audit log** — logins and task/user changes are recorded. Admins can browse
  them under "Audit Logs".
- **External API demo** — the "Directory" page shows contacts fetched from
  JSONPlaceholder, proxied through my backend (see note below on why).
- **Dark mode** — toggle in the top bar, saved to localStorage, defaults to
  your OS preference.

Swagger docs are auto-generated by FastAPI at `/docs` once the backend is
running.

## Stack

Frontend: React 18, Vite, Tailwind, React Router, axios, @dnd-kit (for the
board's drag-and-drop).

Backend: FastAPI, SQLAlchemy 2, Pydantic v2, PyJWT, bcrypt, httpx.

Database: SQLite by default. PostgreSQL works too — just change `DATABASE_URL`
and install the driver.

## Running it

You need Python 3.10+ and Node 18+.

### Backend

```bash
cd backend
python -m venv .venv

# Windows:
.venv\Scripts\activate
# macOS/Linux:
source .venv/bin/activate

pip install -r requirements.txt
uvicorn main:app --reload --port 8000
```

The first time it starts, it creates `internaltool.db` and fills it with demo
data (users, tasks, comments, activity). If you ever want a fresh database,
stop the server, delete that file and start it again.

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Then open http://localhost:5173. Vite proxies `/api` to `localhost:8000`, so
you don't need to configure anything as long as both run on the default ports.

## Configuration

Everything has a working default, so `.env` files are optional. Copy
`.env.example` to `.env` if you want to change something.

Backend (`backend/.env`):

- `DATABASE_URL` — SQLAlchemy connection string. Default `sqlite:///./internaltool.db`.
  For PostgreSQL: `postgresql+psycopg2://user:pass@host:5432/dbname`.
- `JWT_SECRET_KEY` — used to sign tokens. **Change this** if you deploy it anywhere.
- `ACCESS_TOKEN_EXPIRE_MINUTES` — default 480 (8 hours).
- `EXTERNAL_API_BASE_URL` — where the Directory page pulls data from.
- `EXTERNAL_API_TIMEOUT_SECONDS` / `EXTERNAL_CACHE_TTL_SECONDS` — timeout and
  cache duration for the external call.
- `CORS_ORIGINS` — comma-separated, default just the Vite dev server.

Frontend (`frontend/.env`):

- `VITE_API_URL` — only needed if the backend isn't behind the Vite proxy.

## Database

SQLAlchemy creates the tables on startup, so there are no separate migrations
to run. The schema:

**users** — `id`, `name`, `email` (unique), `hashed_password`, `role`, `created_at`

**tasks** — `id`, `title`, `description`, `status`, `priority`,
`assigned_to → users.id`, `created_by → users.id`, `due_date`, `created_at`,
`updated_at`

**comments** — `id`, `task_id → tasks.id`, `user_id → users.id`, `comment`,
`created_at`

**task_activities** — `id`, `task_id → tasks.id`, `user_id → users.id`,
`action`, `detail`, `created_at` (this is the per-task history timeline)

**audit_logs** — `id`, `user_id → users.id`, `action`, `entity_type`,
`entity_id`, `details`, `created_at`

Tasks point at two users (assignee and creator) and own their comments and
activity entries — deleting a task cascades to those. Deleting a user doesn't
delete their tasks, it just unassigns them.

The seed script gives you 4 users and 8 tasks that deliberately cover the
interesting cases: an overdue task, a blocked one, an unassigned one, a couple
of completed ones, and some comments/history so the detail page isn't empty.

## API

The full interactive docs are at `http://localhost:8000/docs` — that's the
easiest way to poke around (log in via `POST /api/auth/login`, then hit
*Authorize* and paste `Bearer <token>`).

Quick reference:

**Auth**
- `POST /api/auth/login` — email + password → JWT and the user object
- `GET /api/auth/me` — current user

**Tasks**
- `GET /api/tasks` — list with query params: `status`, `priority`, `assignee`,
  `search`, `sort_by`, `sort_dir`, `page`, `limit`
- `GET /api/tasks/{id}` — one task including comments and activity history
- `POST /api/tasks` — create
- `PUT /api/tasks/{id}` — partial update (send only the fields you want changed)
- `DELETE /api/tasks/{id}` — admin/manager only
- `GET/POST /api/tasks/{id}/comments` — list and add comments
- `DELETE /api/tasks/{id}/comments/{comment_id}` — your own comments, or admin

**Users**
- `GET /api/users` — everyone (used for the assignee dropdowns)
- `POST /api/users` — admin only
- `PUT /api/users/{id}` — admin only
- `DELETE /api/users/{id}` — admin only, and you can't delete yourself

**Misc**
- `GET /api/dashboard` — the numbers for the dashboard
- `GET /api/external/users` — the JSONPlaceholder proxy
- `GET /api/audit-logs` — admin only, paginated
- `GET /api/health` — sanity check

Some example calls:

```
GET /api/tasks?status=in_progress
GET /api/tasks?priority=high&assignee=2
GET /api/tasks?search=shopify&page=1&limit=20
GET /api/tasks?sort_by=due_date&sort_dir=asc
```

Status codes behave the way you'd expect: `201` on create, `204` on delete,
`400` for bad input (like assigning to a user that doesn't exist), `401`
without a token, `403` when your role isn't allowed, `404` for missing
records, `422` when the request body fails validation. Errors always come back
as `{ "detail": ... }`.

## How the code is organized

```
InternalTool/
├── frontend/
│   └── src/
│       ├── components/   # Button, Input, Select, Modal, Table, Pagination,
│       │                 # StatusBadge, PriorityBadge, TaskCard, KanbanColumn, ...
│       ├── pages/        # one file per screen
│       ├── services/     # one module per API resource + a shared axios instance
│       ├── hooks/        # useAuth, useDarkMode, useDebounce, useTasks
│       └── utils/        # constants, date formatting, error helpers
├── backend/
│   ├── routes/           # HTTP layer only — parse request, call service, return
│   ├── services/         # business logic, activity/audit side-effects
│   ├── repositories/     # the actual SQL queries
│   ├── models/           # SQLAlchemy tables
│   ├── schemas/          # Pydantic request/response models
│   └── utils/            # JWT/bcrypt, auth dependencies, seed script
└── README.md
```

I kept the layers strict on the backend: routes never touch the database
directly, services never build HTTP responses, repositories never know about
FastAPI. It makes the pieces easy to reuse in another internal app — same
reason the frontend components are all generic (the `Table`, `Modal`,
`Pagination` etc. don't know anything about tasks).

## Decisions worth mentioning

- **SQLite instead of PostgreSQL.** The assignment allowed it and it means you
  can run the project with zero setup. The `DATABASE_URL` swap to Postgres is
  a one-line change.
- **No public registration.** New accounts are created by admins from the Team
  page. That matches how internal tools usually work.
- **"Assigned to me" on the dashboard counts open tasks only.** Completed work
  you did in the past isn't really actionable info.
- **The board fetches up to 100 tasks and groups them client-side.** A board
  is a snapshot — paginating columns would be weird UX. The filters still run
  server-side. If a team ever has more than 100 active tasks this would need a
  second look, but for the scope of this tool it's fine.
- **The external call is proxied through the backend** rather than called from
  the browser. That lets me attach a timeout, map failures to proper 502/504
  responses, normalize the response shape, and cache results for 5 minutes so
  we're not hammering a free public API on every page visit. If the external
  API needed a key it would live in the backend env, not in frontend code.
- **Roles are enforced on the server, not hidden in the UI.** The buttons are
  hidden for unauthorized roles, but the API checks again — e.g. a `member`
  calling `DELETE /api/tasks/{id}` directly gets a 403.
